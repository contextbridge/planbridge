# GitHub Inbox Feature Plan

## Overview

Add a new `contextbridge inbox` subcommand that opens a local browser dashboard for engineers and OSS maintainers with large GitHub backlogs. The MVP will use the installed `gh` CLI as the GitHub backend, fetch pull requests and issues that likely need the current user's attention, prioritize them with deterministic heuristics, and render a clean React + Tailwind interface with filtering and GitHub-open affordances.

This should be implemented as a first-class sibling capability, not an extension of the existing annotation flow:

- New CLI command: `contextbridge inbox`.
- New browser UI package: `packages/inbox` (`@contextbridge/inbox`).
- New shared wire schemas in `@contextbridge/shared`.
- New local HTTP routes in `@contextbridge/server` for inbox data and open-in-browser actions.
- Initial GitHub integration through `gh`, fully behind dependency-injected services so a direct GitHub API backend can replace or supplement it later.

MVP behavior:

1. User runs `contextbridge inbox`.
2. CLI verifies usable `gh` authentication, starts a local server, opens the browser, and logs diagnostics to stderr.
3. Browser fetches the inbox snapshot from the local server.
4. UI shows prioritized PR and issue sections for the active user, with repo/time/status filters in UI state and backend query support for the basic filters.
5. Clicking an item opens the corresponding GitHub URL through the local server.
6. The CLI mirrors the current `review` dashboard lifecycle: it stays alive until Ctrl-C. No business payload is written to stdout for the MVP dashboard mode.

## Technical Approach

### Package and command shape

- Add `packages/inbox` as a Vite + React + Tailwind browser UI package, following the browser-package conventions used by `packages/annotation` and `packages/review`:
  - React 19.
  - Tailwind v4 via `@tailwindcss/vite`.
  - `vite-plugin-singlefile` so the CLI can embed a single `dist/index.html` artifact.
  - Import `@contextbridge/ui/styles.css` and reuse shared `@contextbridge/ui` primitives where helpful.
  - Vitest browser-mode tests via Playwright/Chromium.
  - Package-local `AGENTS.md` and load-bearing `CLAUDE.md` stub.
- Add a new CLI command module `packages/cli/src/commands/inbox.ts`, using the existing command conventions:
  - `runInbox(ctx, args)` for the command body.
  - `registerInbox(ctx, program)` for commander registration.
  - `ctx` first in helper arguments, and destructure `ctx` at point of use.
  - Use existing browser-opening and local-server patterns from the `review` command rather than the annotation submission loop.
- Add a CLI bundle shim for the built inbox HTML, matching the existing review/annotation bundle-embedding pattern.
- Register the command in the CLI entrypoint so `contextbridge inbox` appears in help output.

### Shared contracts

Create `packages/shared/src/inboxSchema.ts` with Zod schemas and inferred TypeScript types for the server/UI boundary. Keep timestamps as ISO strings at JSON boundaries and parse/format in implementation with Temporal via `@contextbridge/shared/time`.

Likely contract shape:

- `inboxItemKindSchema`: `'pull_request' | 'issue'`.
- `inboxItemStateSchema`: `'open' | 'draft' | 'merged' | 'closed'` as needed for display; MVP queries should primarily return open items.
- `inboxPrioritySchema`: `'urgent' | 'high' | 'normal' | 'low'`.
- `inboxReasonSchema`: stable reason IDs such as:
  - `review_requested`
  - `assigned_to_me`
  - `mentioned_me`
  - `authored_by_me_needs_attention`
  - `recent_activity`
  - `ci_failing`
  - `dependabot`
- `inboxItemSchema` fields:
  - `id`, `nodeId`, `number`, `kind`, `title`, `url`, `repository`, `owner`, `state`, `isDraft`.
  - `author`, optional `assignees`, optional `reviewRequests`, optional `labels`.
  - `createdAt`, `updatedAt`, optional `lastActivityAt`, optional `mergedAt` ISO strings.
  - Optional PR fields: `baseRefName`, `headRefName`, `reviewDecision`, `checksConclusion`.
  - `priority`, `priorityScore`, and `reasons` generated by the backend.
- `inboxFiltersSchema` fields:
  - optional `repositories: string[]`
  - optional `kinds: ('pull_request' | 'issue')[]`
  - optional `timeWindow: 'today' | 'week' | 'month' | 'all'`
  - optional `includeDrafts: boolean`
  - optional `includeDependabot: boolean`
- `inboxSnapshotSchema` fields:
  - `viewer`, `generatedAt`, `filters`, `items`, and optional `warnings` for partial `gh` query failures.
- Request/response schemas for opening a URL, such as `openInboxItemRequestSchema` and `openInboxItemResponseSchema`.

Use `.trim().nonempty()`/`.nonempty()` for required strings rather than `.min(1)`.

### GitHub data backend through `gh`

Introduce a GitHub inbox service in the CLI/server backend layer that is fully dependency-injected. The service should not call `Bun.spawn` or shell APIs directly from UI/server route handlers; route handlers receive the service through context/options.

Suggested shape:

- Define a small interface, e.g. `GitHubInboxClient` / `InboxDataSource`:
  - `getViewer(): ResultAsync<GitHubViewer, InboxError>`
  - `getInbox(filters): ResultAsync<InboxSnapshot, InboxError>`
  - `openItem(url): ResultAsync<void, InboxError>` or route handler can use an injected opener utility.
- Implement `GhCliInboxClient` using the existing CLI `commandRunner` abstraction from `CliContext`.
- Wrap fallible shell calls, JSON parsing, schema parsing, and URL opening in `neverthrow` `Result`/`ResultAsync` per repo rules.
- Keep all command invocations testable with fake command runners; do not rely on global mocks.
- Validate preconditions before launching the dashboard:
  - `gh --version` is available.
  - `gh auth status` succeeds.
  - `gh api user` or equivalent returns the current viewer login.
- Prefer structured `gh` outputs:
  - Use `gh api graphql` for fields that are hard to get from search, especially review-request state, review decision, and PR metadata.
  - Use `gh search prs` / `gh search issues` with `--json` where adequate and simpler.
  - Parse all command output through Zod schemas before mapping to shared wire contracts.

MVP query strategy can be pragmatic and incremental:

1. Get viewer login.
2. Fetch PRs requesting the viewer's review.
3. Fetch PRs assigned to the viewer.
4. Fetch issues assigned to the viewer.
5. Optionally fetch recent mentions/participation when inexpensive through search queries.
6. Merge and dedupe by GitHub node ID or canonical URL.
7. Apply filters and prioritization.

Default repository behavior:

- If the CLI is run inside a Git worktree with a GitHub remote, default to that repository for initial scope.
- Otherwise query across repositories visible to `gh`.
- Provide CLI options to override this without requiring UI support first:
  - `--repo <owner/name>` repeatable or comma-aware.
  - `--all-repos` to force global search when inside a repo.
  - `--port <port>` if the existing server helper supports it, or follow current local-port conventions.
- The UI should expose a repo filter sourced from returned items for MVP; persistent saved preferences are a follow-up.

### Prioritization heuristics

Start with transparent deterministic scoring. The UI should display both priority buckets and human-readable reasons so users can trust the ordering.

Example MVP scoring:

- `review_requested`: +100, high/urgent depending on age and activity.
- `assigned_to_me`: +80.
- `mentioned_me`: +60.
- `ci_failing` on an authored/assigned PR: +50.
- `recent_activity`: +20.
- Staleness boost for old review requests or long-unanswered assigned issues.
- Dependabot/default bot-authored PRs: lower priority unless assigned to the user, failing, or stale.
- Draft PRs: low or filtered out unless explicitly included.

Map numeric scores to `urgent` / `high` / `normal` / `low` in one backend helper with unit tests. Keep the rules intentionally simple and documented in code so future versions can add user-tunable weighting.

### Server routes

Add inbox-specific route support to `@contextbridge/server` while preserving the existing server context pattern.

Suggested local routes:

- `GET /api/inbox/snapshot?filters...`
  - Parses query params with shared Zod schemas or route-local schemas.
  - Calls the injected inbox service.
  - Returns `inboxSnapshotSchema` JSON.
  - Returns typed error payloads for missing `gh`, auth failure, invalid JSON, rate limiting, and partial query failures.
- `POST /api/inbox/open`
  - Accepts `{ url }` or `{ itemId }` if item lookup is kept server-side.
  - Validates the URL is a GitHub URL from the snapshot or otherwise safe before opening.
  - Uses the existing browser/opener abstraction where available.
- `GET /health` or reuse the current dashboard health route if already provided by the local server helper.
- Static HTML route serving the embedded inbox `index.html`.

If current server helpers are specialized around annotation/review, add a small reusable dashboard server helper rather than duplicating ad hoc `Bun.serve` setup in the CLI command.

### UI design

The initial UI should resemble the supplied clean React + Tailwind dashboard aesthetic:

- Header with product name, viewer login, refresh button, and scope/filter controls.
- Summary cards for urgent/high/normal counts and PR vs issue totals.
- Main content with prioritized sections:
  - “Needs review” PRs.
  - “Assigned to me” PRs/issues.
  - “Mentions / recent activity”.
  - “Lower priority / bots” for Dependabot and similar items.
- Item rows/cards showing:
  - PR/issue icon and number.
  - repo, title, author, labels.
  - last updated / age, using Temporal-derived display helpers.
  - priority badge and reasons.
  - open-in-GitHub action.
- Empty/loading/error states:
  - Loading skeleton or simple spinner.
  - Friendly empty state when there is no attention backlog.
  - Actionable setup error when `gh` is missing or unauthenticated.
  - Partial warning banner if one query fails but others succeed.
- UI filter state:
  - repo selector derived from returned items.
  - PR/issues toggle.
  - time window toggle.
  - include drafts/dependabot toggles.

Use a package-specific frontend context extending `FrontendContext` so analytics/telemetry/logger conventions remain consistent. Avoid direct globals in business logic; isolate `fetch` behind a small client function that is easy to test.

### Instrumentation and logging

- CLI/server diagnostics go through the existing logger and stderr behavior.
- Do not print dashboard data to stdout in MVP.
- Add lightweight analytics events if existing command patterns already do so:
  - `inbox_command_started`
  - `inbox_snapshot_loaded`
  - `inbox_item_opened`
  - `inbox_command_failed`
- Keep analytics/telemetry behind `BaseContext` facilities; no package-local singleton initialization.

## Implementation Steps

1. **Define shared inbox schemas**
   - Add `packages/shared/src/inboxSchema.ts` with item, filter, snapshot, and open-item request/response schemas.
   - Export types inferred from schemas.
   - Add targeted schema tests if shared package patterns include tests for schema validation.

2. **Add the inbox browser package scaffold**
   - Create `packages/inbox/package.json`, `tsconfig.json`, `vite.config.ts`, `vitest.config.ts`, `index.html`, and source files.
   - Add `packages/inbox/AGENTS.md` with package-specific notes and `packages/inbox/CLAUDE.md` stub importing `@AGENTS.md`.
   - Add React entrypoint, package-specific context, API client, and initial app components.
   - Configure single-file Vite build output to `dist/index.html`.

3. **Build the initial inbox UI**
   - Implement layout, cards/sections, filtering controls, item rows, loading/empty/error states.
   - Create small pure helpers for grouping, filtering, and display formatting; put helpers at bottoms of files.
   - Add stories if the Storybook host convention requires package story exports.

4. **Add storybook/root workspace integration**
   - Add `@contextbridge/inbox` to root Bun workspace automatically by placing it under `packages/*`.
   - Add package scripts consistent with browser UI packages: `build`, `typecheck`, `lint`, `test`, and any storybook hooks used by the shared host.
   - Update the shared Storybook host to include inbox stories.
   - Update root/package references only where required for build orchestration or embedding.

5. **Implement GitHub inbox data service**
   - Add a CLI/server-side module for `GhCliInboxClient`, likely under `packages/cli/src/github/` or `packages/cli/src/inbox/` depending on existing command organization.
   - Use `CliContext.commandRunner` for all `gh` invocations.
   - Add Zod parsers for raw `gh` JSON responses near the service implementation.
   - Use `neverthrow` for command execution, JSON parsing, schema parsing, and mapping errors.
   - Implement viewer lookup, auth/status check, query execution, dedupe, filtering, and priority scoring.
   - Add unit tests with fake command runner outputs.

6. **Add server support for inbox dashboard routes**
   - Add route registration/helper in `packages/server` or command-local server wiring if existing server APIs are intentionally thin.
   - Inject the inbox data service and opener dependency.
   - Serve the embedded inbox HTML.
   - Add snapshot and open routes with schema-validated request/response payloads.
   - Add server route tests using fake services.

7. **Add CLI bundle shim**
   - Add the generated/bundle-import shim in `packages/cli` that imports `packages/inbox/dist/index.html` the same way existing browser UI bundles are embedded.
   - Ensure binary/build packaging includes the inbox HTML artifact.

8. **Implement and register `contextbridge inbox`**
   - Add `packages/cli/src/commands/inbox.ts`.
   - Register the command in the CLI program setup.
   - Add CLI options for repository scope and possibly port:
     - `--repo <owner/name>` repeatable or comma-aware.
     - `--all-repos`.
     - `--include-drafts` and `--include-dependabot` if simple to pass through.
   - Preflight `gh` availability/auth before opening the browser and return actionable errors.
   - Start local server, open browser, and block until SIGINT following the `review` command lifecycle.

9. **Round-trip command test**
   - Add a test that runs the command with injected fake `gh` responses and fake browser opener.
   - Verify the local inbox UI server returns an HTML page and `/api/inbox/snapshot` returns the expected prioritized payload.
   - Verify no business payload is written to stdout.

10. **Documentation/help text**
    - Ensure `contextbridge inbox --help` describes the dashboard and `gh` requirement.
    - Add minimal docs/README updates only if the repo currently documents each command in source-controlled docs.
    - Include setup guidance for `gh auth login` in error messages and docs.

## Testing Plan

Run targeted checks during implementation, then finish with `just verify`.

### Shared schema tests

- Valid snapshot parses successfully.
- Invalid required strings fail using `.nonempty()` behavior.
- Filters parse expected defaults/optional fields.
- Open-item request rejects non-GitHub or malformed URLs if the shared schema owns that validation.

### GitHub service tests

Use fake command runner injection; no real `gh` calls in tests.

- Missing `gh` / failed `gh --version` maps to a user-actionable error.
- Failed `gh auth status` maps to an auth/setup error.
- Viewer JSON parses and validates.
- PR review-request, assigned PR, and assigned issue payloads map into normalized inbox items.
- Duplicate results from multiple queries are deduped.
- Filters by repo, kind, time window, drafts, and Dependabot are applied.
- Priority scoring produces deterministic ordering and reason labels.
- Partial query failure can produce warnings without discarding successful query results if that behavior is implemented.
- Malformed JSON and schema mismatches return typed errors through `ResultAsync`.

### Server route tests

- Static route serves the inbox HTML.
- Snapshot route validates filters, calls injected service, and returns `inboxSnapshotSchema` JSON.
- Snapshot route returns typed error payloads for service failures.
- Open route validates URL/input and calls injected opener.
- Open route rejects unsafe or non-GitHub URLs.

### CLI command tests

- Command registration exposes `inbox` in help output.
- Successful `runInbox` starts the server with fake dependencies and invokes the browser opener.
- Preflight failures exit/fail cleanly with diagnostics on stderr and no dashboard stdout payload.
- CLI options are parsed into expected inbox filters/scope.
- Round-trip test: fake `gh` input -> server snapshot -> expected prioritized JSON.

### Browser UI tests

Use vitest browser mode, not Bun test.

- Loading state appears while snapshot fetch is pending.
- Items render in priority order with badges/reasons.
- Repo/kind/time filters update visible items and/or refetch with expected query params.
- Empty state renders for an empty snapshot.
- Setup/auth error state shows actionable guidance.
- Clicking “Open in GitHub” calls the local API client and handles success/failure.
- Accessibility smoke checks for buttons/labels if existing UI test utilities support them.

### Final verification

- Run package-targeted scripts while iterating.
- Before marking implementation complete, run `just verify` from the repo root.
- Do not run root `bun test` directly; use `bun run test` or package-specific test scripts.

## Additional Notes

- Keep the first version intentionally read-only. Actions such as approve, merge, comment, label, close, assign, or “mark triaged” should be follow-ups because they require stronger safety UX and more GitHub permission handling.
- Use `gh` as a replaceable adapter, not as a core domain dependency. The normalized shared inbox contracts should survive a later direct GitHub GraphQL/REST backend.
- Prefer clear prioritization explanations over clever opaque ranking. The target users need to trust why an item appears at the top.
- Treat partial data as a first-class state. Large OSS maintainers may hit rate limits or repository permission edges; the dashboard should show useful results with warnings when possible.
- Do not introduce persistent preferences in the MVP unless storage integration is trivial. UI state and CLI flags are enough for the first implementation.
- Browser-driven shutdown can be a follow-up. MVP should follow the existing `review` command pattern and exit on Ctrl-C.
- Potential post-MVP enhancements:
  - Direct GitHub API backend with token management.
  - Persistent filters/preferences via `@contextbridge/storage`.
  - User-configurable prioritization rules.
  - Team/org dashboards.
  - Notification badges and stale-item aging.
  - Inline triage actions and batched review workflows.
  - Deeper CI/check status integration.
  - `contextbridge inbox --json` non-interactive output mode for scripts.
